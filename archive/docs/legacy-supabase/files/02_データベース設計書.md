# データベース設計書

- 版数: v2.0
- 対象 DB: Supabase (PostgreSQL 15+)
- 前提: 単一プロジェクト・単一運営主体。マルチテナント列を持たない

---

## 0. 移行方針

現行スキーマを直接確認できていないため、**既存を一切壊さない形**で SQL を構成している。

- すべて `create table if not exists` / `create index if not exists`
- `drop` 文は 1 つも含まない
- 同名テーブルが既に存在する場合、SQL はそれをスキップする（＝形が違っても上書きしない）

### 実行手順

1. `sql/00_inspect_current_schema.sql` を Supabase SQL Editor で実行し、現行スキーマを吸い出す
2. 出力を確認し、下表の判断に従う
3. `sql/01_schema.sql` → `sql/02_rls_realtime.sql` → `sql/03_seed.sql` の順に実行

### 同名テーブルが存在した場合の判断

| 状況 | 対応 |
|---|---|
| 列構成がほぼ同じ | 不足列だけ `alter table ... add column if not exists` で追加 |
| 列構成が大きく異なる | 旧テーブルを `rename to xxx_v1` して退避し、新規作成する |
| 使っていない残骸 | `rename to _archive_xxx` で退避（削除しない。当日まで消さない） |

**リハーサルデータ（`[REHEARSAL]` イベント）は移行対象外。**
新スキーマ側で作り直す。

## 2. 主要テーブルの設計意図

### 2.1 `events`

大会ごとに変わるものはすべてここに集約する。演出テンプレートは 1 本のまま。

| 列 | 意図 |
|---|---|
| `title` / `subtitle` | 「20周年トーナメント」「第○○回」を差し込む。更新.md 項目 4 |
| `team_size` | 1 = シングルス / 2 = ダブルス / 3 = トリオス。将来拡張を列 1 本で吸収 |
| `draw_mode` | 抽選モード。演出側はこの値を参照しない（原則 1） |
| `status` | 編集ロックの基準。要件定義 3.5 の表に対応 |
| `show_scores` | レグ得失点の表示 ON/OFF。データは常に格納可能 |
| `theme` (jsonb) | 配色の上書き。既定値はコード側の定数 |
| `settings` (jsonb) | 演出の尺など。**新項目の追加にマイグレーション不要** |
| `admin_token` | Admin URL に含めるトークン。アプリ層で検証 |

### 2.2 `event_state` — 最重要テーブル

**1 イベント 1 行。Display はこの行だけを購読する。**

| 列 | 意図 |
|---|---|
| `scene` | 現在のシーン。要件定義 3.1 の 10 種 |
| `scene_payload` (jsonb) | 対象 match_id、演出パラメータなど |
| `scene_seq` | **遷移のたびに +1。Display は自分の seq 以下の更新を破棄する** |
| `awaiting_operator` | 手動クローズ待ちフラグ。更新.md 項目 1 |
| `current_match_id` | 現在の対象試合 |
| `presentation_mode` | `full` / `short` / `lite`。緊急時に Admin から即座に落とせる |

`scene_seq` は Realtime の順序逆転・重複配信に対する唯一の防御である。省略しないこと。

### 2.3 `draw_sessions` — 原則 1 の実体

| 列 | 意図 |
|---|---|
| `mode` | どのモードで組んだか（記録用。演出は参照しない） |
| `seed` | 乱数シード。同じ抽選を再現できる |
| `reveal_order` (jsonb) | 参加者 ID の配列。**先頭から `team_size` 人ずつ組にすると確定チームが再現される** |
| `committed_at` | 確定時刻。null の間は下書き |

演出コンポーネントは `reveal_order` を順に描画するだけでよい。
`full_random` と `rating_balanced` の差はこの配列の作り方だけに閉じ込められる。

### 2.4 `matches`

`brackets-manager` で進行計算をしていても、**表示・座標・復帰のために結果を DB に持つ**。

| 列 | 意図 |
|---|---|
| `bracket` | `winners` / `losers` / `grand_final`。**テーマ切替のキー**（要件定義 3.3） |
| `next_win_match_id` / `next_win_slot` | 勝者の行き先。進行を DB 上で追跡可能にする |
| `next_lose_match_id` / `next_lose_slot` | 敗者の行き先。ダブルイリミの肝 |
| `sequence` | 進行順。「次の試合」の決定に使う |
| `layout` (jsonb) | 座標駆動レイアウトの座標値 |
| `score_a` / `score_b` | 常に格納可能。表示は `events.show_scores` |

`next_*` を持つことで、1 手戻す際に「どこへ進めたか」を逆算せず参照できる。

### 2.5 `operation_log` — 1 手戻す

**逆操作を計算するのではなく、変更前スナップショットを復元する方式。**

| 列 | 意図 |
|---|---|
| `action` | `confirm_result` / `scene_change` / `edit_rating` など |
| `target_table` / `target_id` | 対象 |
| `before` / `after` (jsonb) | 変更前後の行全体 |
| `undone_at` | 取り消し済みなら時刻。null が有効な履歴 |

1 手戻す = `undone_at is null` の最新行を取り、`before` を書き戻して `undone_at` を立てる。
逆操作の計算は分岐が増えるほど破綻するため採用しない。

### 2.6 `media_assets` — Storage / 外部 URL 両対応

| 列 | 意図 |
|---|---|
| `source` | `storage` / `external` |
| `storage_path` | Supabase Storage のパス |
| `external_url` | YouTube 等の URL |
| `has_alpha` | 透過 WebM の判別。合成方法が変わる |
| `preload` | 事前読み込み対象か。プリロード進捗表示に使う |
| `sponsor_id` | 広告主との紐付け。レポート用 |

CHECK 制約で「storage なら path 必須 / external なら url 必須」を保証する。

**運用指針:** 確実に流したい注意事項は Storage。差し替えが多い広告は外部 URL。
外部埋め込みは自動再生・ループ制御が提供側の仕様に依存するため、
Admin 画面でその旨を注意表示する。

### 2.7 `playlist_items` の並べ替え

`order_no` を **numeric** にしている。整数だと項目を間に挿入するたびに
後続を全件更新することになるため。

- A(1.0) と B(2.0) の間に挿入 → 1.5
- 精度が枯渇したら振り直しバッチを回す（実運用では発生しない想定）

一意制約は付けない（並べ替え中の一時的な重複でエラーになるため）。

### 2.8 `ad_impressions`

表示のたびに 1 行。後付けが困難なため初期実装に含める。

集計例（スポンサー報告用）は `sql/04_reports.sql` を参照。

## 3. RLS 方針

Admin のアクセス制御は URL + イベント ID 共有方式（要件定義 4.3）。
したがって RLS は認証ベースの制御を行わず、以下 2 点のみを担う。

1. **終了済みイベントの保護**: `events.status = 'finished'` の配下データは更新・削除不可
2. **ログの改ざん防止**: `operation_log` / `ad_impressions` は insert のみ許可、update / delete 不可

これは「悪意ある第三者を防ぐ」ものではなく、**当日の誤操作から守る**ためのもの。
セキュリティ境界は URL の秘匿に依存していることを明示的に受け入れる。

## 4. Realtime 設定

購読対象は最小限にする。購読テーブルが増えるほど再描画が増え、演出が引っかかる。

| テーブル | 購読 | 理由 |
|---|---|---|
| `event_state` | **必須** | シーン遷移。これだけで演出の 9 割が駆動する |
| `matches` | 必須 | ブラケットの反映 |
| `teams` / `team_members` | 必須 | 抽選確定の反映 |
| `participants` | 任意 | エントリー画面のみ |
| その他 | 不要 | Admin 操作時に都度取得する |

---

## 5. インデックス方針

- 外部キー列にはすべてインデックスを張る（`on delete` 時のフルスキャン回避）
- `matches (event_id, sequence)` — 「次の試合」の取得
- `matches (event_id, bracket, round)` — ブラケット描画
- `operation_log (event_id, id desc) where undone_at is null` — 1 手戻す対象の取得
- `ad_impressions (event_id, media_id)` — レポート集計

## 6. 命名規約

| 対象 | 規約 |
|---|---|
| テーブル | 複数形・スネークケース（`matches`, `playlist_items`） |
| 主キー | `id`（uuid、`gen_random_uuid()`） |
| 外部キー | `<単数形>_id`（`event_id`, `team_a_id`） |
| 真偽値 | `is_` / 動詞（`is_locked`, `enabled`, `preload`） |
| 時刻 | `_at` 接尾辞（timestamptz） |
| 状態列 | text + CHECK 制約。**enum 型は使わない**（値の追加を容易にするため） |
| jsonb | 拡張の受け皿。検索対象にする場合のみ GIN インデックスを検討 |
