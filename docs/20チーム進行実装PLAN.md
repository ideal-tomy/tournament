# 20チーム・ダブルイリミネーション進行の実装PLAN

対象は20チーム（40人）、ダブルイリミネーション、2台だけにする。人数や形式をまたぐ共通ルールは作らない。

会場表示と演出は変えない。カメラ、ブラケットの見た目、画面遷移、会場の台カードも含む。

運営ページは、優先試合の確認、手動選択、並行進行への切替に必要な変更だけを行う。台カードの並べ替え、横並びへの変更、それ以外のデザイン変更は行わない。

## 運営の形

各台の主ボタンは今のままにする。

- 空き、または勝者確定のあと: 「次の試合を入れる」。入るのは、その時点の優先試合だけ。
- 呼び出し中: 「試合開始」。割り当てただけでは始めない。
- 試合中: 勝ったチームを選んで確定。

押した台だけを埋める。今のサーバーは、1回の操作で空いている台をすべて埋める。ここを、押した台だけに変える。もう一方が空いていても、その台のボタンを押すまで入れない。

今ある「次の試合」の欄に、次に入る試合を常時出す。区分と回戦、2チーム、選ばれた理由を書く。出せないときは、その台のボタンを止めて、理由を同じ欄に出す。

- 対戦相手の確定待ち
- 出場チームが別の台で試合中、または確保済み
- 今の段階では出さない
- 大会終了

理由の文は運営ページ用である。会場には出さない。進行デバッグの折りたたみは、この欄へ移したら畳んだままにしない。

## 段階

無敗が4チームになるまで、ウィナーズの実試合を進める。不戦勝は数えない。準決勝は、片方の相手が決まっていても出さない。

今の不戦勝配置では、その実試合は16である。内訳は、1回戦4、両者すでに決まっている2回戦6、1回戦の勝者同士の2回戦2、3回戦4。この内訳は、今の配置での検証例である。不戦勝を分散した配置では、初戦のチームと1試合済みのチームが対戦する試合もできる。試合数はこの16に固定しない。

### A. ウィナーズだけ

無敗が4チームになるまで、2台ともウィナーズだけを出す。

実試合がゼロ同士を先にする。今の配置では、開始時に出せるのは1回戦4と、不戦勝チーム同士の2回戦6である。同じ条件なら下の回戦を先にする。1回戦が1試合残っていても、空いた台には、すでに両者の決まっている2回戦を入れる。ゼロ同士が残っているあいだは、1試合済みのチームが入る試合を後回しにする。

手動選択は、全20チームの実試合数が1以上になるまで出さない。このあいだは「次の試合を入れる」だけを使う。10試合終了では判定しない。

### B. ルーザーズだけ

無敗4チームが確定したら、ウィナーズを止めてルーザーズだけを出す。両チームが決まっている試合から選ぶ。下の回戦を優先し、その回戦が試合中でも、依存しない別の試合は空いた台へ入れる。

段階Bに入った時点から、「ウィナーズも同時に進める」を押せる。ルーザーズの候補が残っていても、運営者が再開を判断できる。出せるルーザーズが尽きたときは、切替を促す。準決勝を出せば動く場合と、準決勝の敗者が来ないと相手が決まらない場合は、理由で分けたままにする。

### C. 両方

「ウィナーズも同時に進める」を押したあと、ウィナーズとルーザーズの両方を候補にする。台を区分で固定しない。押すまで準決勝は出さない。切替のタイミングを、回戦数や残りチーム数へ自動では置き換えない。

グランドファイナルと、必要になったリセット戦も、両チームが決まったときだけ同じ候補に入れる。

## 候補と優先

候補は、次をすべて満たす試合だけにする。手動で選ぶときも同じ条件から外れない。

- 今の段階で出してよい
- 両チームが決まっている
- 未開始かつ未終了
- 両チームとも、別の台で試合中ではない
- 両チームとも、別の試合へ確保済みではない
- 不戦勝の自動進出ではない

優先は次の順にする。

1. 実試合がゼロ同士の対戦。不戦勝で上の段へ進んだチームも、実試合がゼロとして扱う。
2. 他に候補があるときは、直前に終わったチームの連戦を避ける。他になければその試合を出し、連戦になる理由を結果に残す。
3. 2チームのうち休憩が短い側を比べ、長く休んでいる対戦を先にする。
4. 同じ区分の中では、下の回戦、表の左から右、試合IDの順。ウィナーズの回戦番号とルーザーズの回戦番号は比べない。段階Cでここまで同じときは、長く待っている側を先にする。

休憩は試合の終了時刻で計算する。回戦内の試合番号は使わない。実試合がゼロのチームの待ちは、2台を開いた時刻から数える。不戦勝を処理した時刻は、最終試合の終了時刻にしない。最低休憩で台を止める処理は足さない。

呼び出し中の試合は、別の結果が入っただけでは入れ替えない。両台の割り当てが同時に走っても、同じ試合と同じチームを二重に取らない。

手動で入れ替えたあとは、残った候補から優先順位を計算し直す。対戦相手、勝ち上がり先、敗者の移動先は変えない。

## 全員の初戦が終わったあとの入替

手動選択の解禁は、全20チームについて、不戦勝を除いた実試合の終了数が1以上になったときにする。今の配置では、1回戦4と不戦勝同士の2回戦6が終わった時点がこれにあたる。この10試合は検証例であり、解禁条件には使わない。

開けるのは、空きの台と、呼び出し中でまだ開始していない台だけにする。試合中の台と、勝者演出が終わっていない台は変えられない。

一覧に出すのは、上の候補条件を満たす試合だけである。相手が片方しか決まっていないルーザーズは出さない。各行に、区分と回戦、2チーム、それぞれの実試合数と休憩、優先ならその表示を出す。

選択を確定するとき、サーバーで条件を取り直す。一覧を開いたあとにもう一方の台が進んでいても、その時点の確保と段階で判定する。条件を満たさなければ拒否し、元の呼び出しを維持する。

入れ替えは一つの処理にする。元の試合とチームの確保を解除し、新しい試合とチームを確保する。途中で失敗した場合は、元の呼び出しを維持する。成功したときだけ、その台の呼び出しが新しい試合に替わる。

もう一方の台の優先試合は、入れ替え後の確保を除いて計算し直す。その後の「次の試合を入れる」は、残った候補の一位を入れる。手動のあとも、条件を満たす台では一覧から選び直せる。

変えてよいのは、どの試合を、どの台で行うかだけである。

## 実装の順

### 1. 20チーム専用の候補選択

`src/features/progression/` に、20チーム・2台のときだけ使う選択を置く。既存の `getChapterMatches` は、1台進行と他の人数のために残す。2台の補充は、20チームのときだけ新しい選択を使う。

入力は、ブラケット、段階（A / B / C）、各台が確保している試合、各チームの実試合数、試合終了時刻、2台を開いた時刻、仮想または実時刻。出力は、優先順の候補、一位を選んだ理由、空き理由、手動選択を解禁してよいか、段階Bで切替を促すか。

手動解禁は、全20チームの実試合数が1以上かで返す。試合の本数では返さない。切替を促すのは、段階Bでルーザーズの候補が尽きたときだけにする。段階Bの開始直後から切替自体は可能、というフラグも返す。

終了時刻は `event_state` の画面データへ、試合IDごとの文字時刻として残す。2台を開いた時刻と段階も同じ場所に残す。状態列の型は足さない。

ここまでを、仮想時計のシミュレーションで大会終了まで確認する。試合時間は長短を混ぜる。確認することは次のとおり。

- 台1が先に終わる場合と、台2が先に終わる場合
- 片方だけ試合が長い場合
- 不戦勝の位置が違う場合。手動解禁がその配置でも「全チームの実試合数が1以上」で起きること
- 勝敗が違う複数パターン
- 無敗4チームで準決勝を出さないこと
- 段階Bでは、切替前はウィナーズを出さないこと。段階Bの開始直後から切替でき、候補が残っていても切替できること
- 段階Bで候補が尽きたとき、切替を促すこと
- 段階Cのあと、両方と最終戦を候補にできること
- 同じ試合、同じチームを二重に取らないこと
- 呼出中の入替で、元の確保が外れ、新しい確保が一つで行われること。失敗時は元の呼出が残ること
- 手動指定のあと、残りの候補から優先が計算し直され、ブラケットが完走すること
- 決勝リセットありとなし
- 空いた時刻に、出せる候補が本当になかったこと

各割り当ては、仮想時刻、台、試合ID、区分と回戦、2チーム、各チームの実試合数と休憩、選択理由を記録する。

既存の「1回戦の最後が試合中なら、決まっている2回戦を出さない」は、8チームなど今の経路の回帰として残す。20チームの2台は、その回帰へ入れない。

### 2. 台の操作へ接続する

`cloudflare/checkin/src/flow.ts` の2台進行で、20チームのときだけ新しい選択を使う。

- 「次の試合を入れる」は、押した台へ優先試合を置く。
- 手動の操作は、確定時に候補条件をサーバーで再確認する。全チームの実試合数が1以上になるまでは拒否する。空きまたは呼び出し中以外の台も拒否する。
- 呼び出し中の入替は、元の試合とチームの確保解除と、新しい試合とチームの確保を一つの処理にする。失敗したら元の呼び出しを維持する。
- 「ウィナーズも同時に進める」は、段階Bに入った時点から受け付ける。画面データ上の段階をCへ進める。戻す操作は作らない。段階Aでは拒否する。
- 勝者確定のとき、その試合の終了時刻を残す。instant の自動進行も同じ選択を使う。
- ルーザーズへ入る直前の会場確認は、今の秒数のまま残す。確認が終わるまで、その台への割り当てと開始は今どおり止める。

`src/checkin/rehearsalAutoplay.ts` は、空いた台ごとに今の「次の試合を入れる」を送る。優先試合をボタンで入れる形と揃える。

### 3. 運営ページ

`src/checkin/OperatorPage.tsx` に、確認と操作だけを足す。台カードの配置と見た目は変えない。会場の `CourtBoards.tsx` は変えない。

- 今の「次の試合」欄に、優先試合と選ばれた理由、出せない理由を出す。
- 全20チームの実試合数が1以上になったあと、対象の台に「別の試合にする」と候補の一覧を出す。
- 段階Bに入った時点から「ウィナーズも同時に進める」を出す。出せるルーザーズが尽きたときは、そのボタンを促す表示にする。

APIの戻りに、優先試合、選択理由、候補一覧、空き理由、段階、手動が使えるか、切替できるか、切替を促すかを足す。`src/checkin/DrawControl.tsx` の流れの型もそれに合わせる。会場コンポーネントはこの戻りを表示に使わない。

## 完了の見方

- 20チーム・2台のシミュレーションが、上の確認項目を通っている。
- 運営ページで、優先試合をボタン一つで台へ入れられる。
- 全チームの実試合数が1以上になったあとだけ、確定済みの候補から入れ替えられる。入れ替えは一つの処理で、失敗時は元の呼出が残る。成功後の優先試合は、残りの候補から計算し直されている。
- 段階Bの開始時から並行へ切り替えられ、ルーザーズの候補が尽きたときは切替が促される。
- 会場の表示と演出ファイルに差分がない。運営ページは、上記の確認と操作以外の配置変更がない。
- 8チームなど、今回の対象外の既存テストが壊れていない。

未接続のまま残すものはない。段階の切替と手動の指定は、このPLANの運営ページまでつなぐ。
