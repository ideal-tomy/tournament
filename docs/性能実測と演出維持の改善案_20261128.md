# 公開環境の性能実測と、演出を維持する改善案

調査日: 2026-11-28。既存の終了済み公開リハーサル大会（8名・4組）を対象に、既存のMicrosoft EdgeをPlaywrightでヘッドレス起動し、ブラウザのResource Timing・PerformanceObserver・requestAnimationFrameで計測。表示サイズ1280×720、各画面約15秒。実際のネットワークと公開Workerを使用。新規依存の追加やデプロイはなし。大会更新を防ぐため認証以外のAPI更新要求はブロックした。数値はこのPC・回線・この1回の観測であり、会場端末・回線や他の参加者数を代表しない。公開版と作業中ソースは一致確認していない。

## 主な結果

| 項目 | 実測 | 解釈 |
| --- | --- | --- |
| 運営画面の状態API | 15回、222〜309 ms、約2.1 KB/回（Resource Timingの転送サイズ） | 毎秒の取得は確認できた。Worker・D1・回線の内訳は未測定 |
| 会場画面の状態API | 14回、243〜570 ms | 先読み中も取得。DB自体が遅いとは判別できない |
| 会場画面の静的画像 | 複数の大きな画像が約4〜6秒 | 並列取得時の各要求の経過時間であり、単独でのダウンロード速度ではない |
| 写真 | 8件、250〜686 ms/件 | 並列取得。画像は検証データで約3〜4 KB/件、実写真や大人数では別途測定が必要 |
| ペア発表の確認再生、初回15秒 | 全リソース転送29,319,795 bytes、うち演出素材28,296,317 bytes（約27.0 MiB） | 表示直後に大量の素材が先読みされる |
| 続くVS確認再生、15秒 | 演出素材27,875,405 bytes（約26.6 MiB） | 同じブラウザ内の次の画面でも大きな転送が再発 |
| 静的PNGの応答ヘッダー | `Cache-Control: public, max-age=0, must-revalidate` | 再訪問時の再検証が必要。実際に上記測定では再転送が見られた |
| ペア発表のフレーム間隔 | 中央20.8 ms、95パーセンタイル41.6 ms、最大484.6 ms、50 ms超20回 | 計測環境では表示間隔の乱れを観測。ヘッドレス描画のため会場でのfpsの実測値とは扱えない |
| ペア発表の長い処理 | 170、58、54、434 ms | メインスレッド上の長い処理を観測。処理の内訳・原因は未特定 |
| VSのフレーム間隔 | 中央7.0 ms、95パーセンタイル14.3 ms、最大221.7 ms、50 ms超6回 | 同上。シーン間の相対差も実端末で再確認が必要 |

Resource Timingの転送値には応答ヘッダー等を含みます。二つの演出確認は同じコンテキストで順番に実施しており、初回と再訪問の条件が完全に同じ比較ではありません。状態APIの取得時間はブラウザ側の全経過時間で、D1単独の処理時間ではありません。音声はブラウザの自動再生制限によりタップ待ちで、音響や実際の音声再生中の負荷は未確認です。リソース取得が中断された音声要求が2件あり、これだけで配信障害とは断定できません。

## 演出の見た目・タイミング・音を変えずに検討できる改善

1. **静的素材をバージョン付きURLで配信し、適切な長期キャッシュを設定する。** 同じ素材の再取得を減らす有力候補。現状の演出素材は固定名なので、単に長期キャッシュを付けると更新後に古い画像・音声が残る危険があります。内容ハッシュ付きファイル名等とセットで変更し、公開後の更新・戻し・別端末を確認します。認証付き写真や大会状態には同じ公開キャッシュを適用しません。
2. **先読みの順序と同時数を制御する。** 演出開始までに必要な素材は準備済みとし、後のシーン用を余裕のある時間に取得する。画面・音・演出時間を変えずに初期の通信集中とデコード負荷を減らせる可能性があります。早い操作や低速回線でも必要素材が間に合うことを確認し、準備未完了時に演出が欠けないようにします。
3. **画像を見た目を維持できる範囲で最適化する。** 実表示サイズ、透過、画質を比較し、可逆圧縮や適切な画像形式を検討します。ピクセル完全一致が必要なら可逆方式に限定し、素材の見え方と切替のタイミングを実機で照合します。先読みとキャッシュの改善だけで十分かを先に測定できます。
4. **状態取得の中身・DB問い合わせを計測して削減する。** 画面上の同期・自動進行の仕様を守ったまま、変化しないデータの再送や重複問い合わせを減らす余地を検討します。今回の値からDBだけを原因と決めることはできません。Worker内の区間時間、SQL実行計画、複数画面・大人数での遅延を先に測ります。
5. **写真の先読みを必要順に分散する。** 全員の顔が必要になる前に準備し、同時要求を制御する。顔の表示タイミングを変えない条件で、失敗時・写真更新時・人数増加時も確認します。今回の8枚の小さい検証写真では、写真が主因という根拠はありません。

## 次の検証

会場で実際に使うブラウザ、解像度、ネットワーク、想定参加人数と画面台数で、音声有効時の初回・再訪問を比較します。Performanceトレースで長い処理の関数と画像デコード、フレーム落ちを確認し、同時に状態API・写真APIの応答とWorker側の区間時間を測ります。ネットワークログには参加者情報や認証情報を含めないようにします。変更後は同条件で転送量、表示開始、演出のフレーム間隔、音と画の同期、端末間の反映時間を比較します。

今回の結論は、**演出を変えずに改善できる可能性はあるが、効果と完全な同一性は変更後の実機検証が必要**というものです。特にキャッシュと先読みの見直しは、今回観測した素材転送量に直接対応します。
