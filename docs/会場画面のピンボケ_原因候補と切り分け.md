# ダーツ大会の会場画面が揺れてぼけるときの調査手順

対象は、登録済みの顔写真が2回戦から3回戦の枠へ入る場面。「表示を確認する」でも再現する。2026年11月20日の添付記録を基にした調査案。実装・公開画面・会場機材での再現試験は今回行っていない。

**最初に見たいのは、顔写真が着地した瞬間と、表が二重に映り始めた瞬間が同じかどうか。** 記録上、着地は演出開始から約2秒、寄った表と全体の表を重ねるのは3〜6秒。この約1秒の違いで、調べるコードが変わる。さらに「画面全体」に、表の外にある固定文字まで含まれるかを確かめたい。

## 1．すでに試したことから分かる範囲

| 試した変更 | 結果から読み取れること |
| --- | --- |
| ルーザーズ表で、同じ対象へのカメラ再計算を抑制。枠の影を22pxから最大8pxへ縮小 | 症状は残った。同じ対象への再計算や大きな影だけでは説明しきれない |
| ルーザーズ表の倍率を固定し、移動の補間も停止。ウィナーズの追加CSS拡大を削除 | ローカルのルーザーズでは倍率0.8561を維持したまま位置が約338px変化。ウィナーズのSVG内の表示範囲、祖先の変形、2枚の表の位置関係は別途確認が必要 |
| ウィナーズ枠と接続線のSVGガウスぼかしを削除。色・線幅の変化に置換 | ローカルで対象SVG内のfilterは0件。症状は残った。他画面の背景や親要素にかかるCSS、透明なレイヤーの重なりは未確認 |
| 登録済みの写真で確認 | 仮画像固有の問題は対象外。実写真の読み込み・描画と着地処理の関係は未計測 |

記録上の公開版は `c7e910a9-eec9-45a1-8ca5-4491902c8d39`。最初の報告があった版は `717d0d10-2686-47ab-b17f-a794039ebc31` の後。発生し始めた版はまだ特定できていない。

## 2．最初の再現で採る証拠

1. リハーサル用の同じ試合・同じ登録写真を使う。「表示を確認する」で、2回戦の静止状態から、3回戦の演出が終わったさらに2秒後まで録画する。画面サイズ・ブラウザ倍率・全画面の有無・表示先を記録し、比較中は固定する。
2. 診断用に小さな「固定 ABC 123」と白黒の縦線を、ブラケットや演出コンテナの**外**に置く。表の中では、進出先から離れたチーム名と縦線を目印にする。着地する写真を含め、3か所を同時に見る。
3. 録画をコマ送りし、①着地直前 ②着地した最初のコマ ③2枚の表が透け合っている途中 ④演出終了後を、同じ範囲・等倍で比較する。PCの元画像を使い、共有サービスの縮小プレビューは比較から外す。
4. 開発側では、演出開始・着地処理・各表の表示開始／終了・状態取得の反映に時刻を付ける。可能なら、その時点の旧表／新表の実効opacity、viewBox、共通の試合枠の画面座標を残す。タイマーの予定時刻と実際に表示されたコマは区別する。

| 見え方 | 次に試すこと |
| --- | --- |
| 3〜6秒だけ、離れたチーム名や枠にも二つの輪郭が見える。固定文字は鮮明 | 寄った表だけ／全体の表だけをそれぞれ同じ時点で表示。単独では鮮明かを見る |
| 2秒付近ですでに表全体が揺れ、まだ2枚目は見えていない | 着地の前後1コマで表の座標・幅・高さ・viewBoxとDOMの入れ替わりを比較 |
| 約1秒ごとに繰り返す、または演出終了後も同じ動きが戻る | サーバーからの状態反映、演出の開始回数、残ったタイマーの順序を突き合わせる |
| 固定文字まで同じコマで変わる | 固定文字にもかぶさる全面レイヤー、最上位要素、ブラウザの合成、表示機器へ進む |
| 写真だけが甘く、文字と縦線は鮮明 | 配信画像の実寸、着地後の表示寸法、写真の二重表示を優先 |
| PCで保存した静止画は鮮明、動いている会場モニターでは揺れる | コマ間の位置の往復、フレーム落ち、モニター側の動画処理を比較。静止画1枚でアプリ側を除外しない |

## 3．原因候補と、個別に確かめる方法

上から順にすべて変更する必要はない。上の表で該当した行から進む。「優先」は今回の発生範囲・タイミングと合い、少ない変更で判別できるもの。「条件付き」はその機能・機材を実際に使用している場合の候補。

### A．表を重ねる演出と、写真の着地処理（優先）

| 候補 | 見分けるテスト |
| --- | --- |
| 寄った表と全体表のクロスフェード。同じ名前や線が異なる座標に一緒に映る | `AnimatedBracketAdvance` の3〜6秒を途中で止める。両方→旧表だけ→新表だけと表示を変え、同じ文字を比較。位置と時間を動かさず濃度だけ変える |
| 想定より早い重なり。新旧レイヤーの初期opacity、入場／退場クラス、前の画面の消し残り | 約2秒時点で存在する全面要素と実効opacityを確認。各要素を一枚ずつ不可視にする。DOMに2枚あるだけでは原因と判定しない |
| 飛んでいる写真、元枠の写真、着地点の写真が同時表示される | 着地の直前直後で移動用の複製だけ隠す。写真の二重像だけ消え、離れた枠がまだ揺れる場合は別要因も調べる |
| 着地を合図に画面全体へ衝撃・フラッシュ・振動のクラスが付く | 写真から親をたどり、着地時に増えたanimation、transform、個別のtranslateやscaleを確認。該当アニメーションだけ止める |
| 線幅の2.5→4、外周線の点灯、ルーザーズ枠の影、走る線が揺れに見える | 光る枠と離れた文字を一緒に見る。点灯だけ静止しても文字まで揺れるなら調査を続ける。光と線は診断後に戻す |
| 重なったSVGでclipPath、mask、patternなどのIDが重複する | 同時表示される2枚でIDと参照先を照合。異常のある参照だけインスタンスごとに一意にして比較。削除済みのガウスぼかしとは別の候補 |

### B．画面サイズ、カメラ、描画座標（着地時点ですでにぶれる場合に優先）

| 候補 | 見分けるテスト |
| --- | --- |
| 回戦切替でSVGのviewBoxが飛ぶ、または複数処理が交互に書き換える | CSSのscaleを止めた状態でも、両SVGのviewBoxと同じ試合枠の座標を毎フレーム記録。演出中だけ片方の書き込み元を止めて比較 |
| 親の画面フィット倍率、CSS zoom、全画面用コンテナ、SVG内の変換が重なる | SVGの外側から画面ルートまでの実効transformと矩形を採る。診断時のみ祖先の倍率を1にし、同じ枠を等倍で比較 |
| 小数倍率・端数座標で細線や文字の縁が揺れる | 固定倍率のまま移動も停止し、静止中の甘さと移動中のちらつきを比較。位置を実デバイスの画素境界に一時的に揃えて再比較。0.8561はルーザーズの観測値 |
| 写真追加、フォント読込、ラウンド名の改行、スクロールバーで親の寸法が変わる | 着地前後で親・表・枠の矩形を採る。写真枠の寸法、フォント、親サイズを個別に固定し、最初に寸法が変わる要素を探す |
| ResizeObserverやサイズ計測が自分の更新を拾い、2種類の配置を往復する | 連続するコマで幅または位置が A→B→A と戻るか確認。入力寸法が同じ計測結果の再適用だけ止める |
| 手動カメラと自動スクロール、フォーカス移動、開幕ツアーの残存処理が競合する | scroll位置、activeElement、カメラ処理の開始／破棄を記録。開幕を経由した場合と直接プレビューした場合を比較 |
| CSS transitionとJSのフレーム更新が同じ要素を動かす | 書き込まれた値と実効座標を同時に採り、対象のtransitionだけ一時停止。`.losers-track` 以外の祖先・子も確認 |

### C．約1秒ごとの状態取得と画面の作り直し

| 候補 | 見分けるテスト |
| --- | --- |
| 内容が同じ応答でも新しいオブジェクトが届き、演出のEffectが再始動する | 状態取得回数と演出開始回数を別々に記録。同一スナップショットを繰り返し与え、試合・進出先が同じなのに再始動するかを見る |
| keyが変わって表が再マウントされ、透明度・位置・写真が初期値に戻る | 描画更新とmount/unmountを区別して記録。着地で同じ表のDOMが入れ替わるかを見る |
| 遅い応答が新しい応答の後に届き、2回戦と3回戦を往復する | 各要求の開始・完了・適用順と、試合ID・回戦・状態の版を照合。状態が実際に巻き戻るか確認 |
| 古いタイマー、requestAnimationFrame、animationendなどが次の演出にも作用する | 演出1回ごとに識別子を付け、終了後のコールバックを記録。初回と、同じ操作を2回目に行った場合を比較 |
| 着地用のローカル状態、勝敗確定、サーバーで確定した写真の反映が別々に走る | 同じ進出先への更新を時系列に並べ、どの更新で最初に画面が変わるか確認。取得済みの状態列をローカル再生すると比較しやすい |

**状態取得を試すとき**は、演出を起動する状態が届いた後、同じ演出を最後まで再生できる条件で、後続応答の画面反映だけを保留する。通信を切って演出そのものが起きなくなった結果は判定に使えない。

### D．全面レイヤー、画像、描画負荷

| 候補 | 見分けるテスト |
| --- | --- |
| セレモニー・VS・待機背景の全面要素が退場後も表にかぶさり、backdrop-filterや半透明色が効く | 症状が出ているコマで最前面の要素と覆う矩形を確認。該当レイヤーだけ隠す。背後にある背景自身のblurと、手前から背面をぼかすbackdrop-filterを区別する |
| 擬似要素、画面切替用の旧画面スナップショット、動画・Canvasの残像（使用時） | 通常のDOM以外に ::before／::after、画面遷移効果、全面Canvasがあるか確認。存在するものだけ個別に停止 |
| 描画済みレイヤーを一時的に拡大して表示している | 表単独で枠・文字まで一様に甘く、数コマ後だけ鮮明になる場合。祖先のwill-changeや3D変形を一つずつ外し、同じ座標・倍率で比較 |
| 低解像度画像、サムネイルから本画像への切替、元写真の圧縮・切り抜き拡大 | 実際に選ばれた画像URL・ピクセル寸法と、着地後の表示寸法×端末画素比を比較。写真だけ鮮明度が変わるか、元画像を直接表示して確認 |
| 大きな写真のデコード・転送、2枚の表、紙吹雪・背景動画の同時描画でコマが飛ぶ | ChromeのPerformanceで着地前後を記録。画像を同寸の単色素材にした場合、写真を先読みした場合、紙吹雪だけ止めた場合を別々に比較。コマ落ちだけで静止画の二重輪郭までは説明できない |
| Canvasや中間画像の内部解像度が表示サイズより小さい（使用時） | 内部ピクセル寸法とCSS上の寸法を比較。表全体を一枚の画像にしている箇所がある場合のみ、直接描画との比較を行う |
| ブラウザ・GPU・ドライバ固有の合成不具合 | 同一PC・同一表示条件で別エンジンのブラウザと比較。その後、必要ならグラフィックスアクセラレーションの有無を比較。改善してもGPU故障とは断定できない |

### E．プレビュー環境と会場の表示経路（環境差がある場合）

| 候補 | 見分けるテスト |
| --- | --- |
| 「表示を確認する」の親画面や埋め込み枠でさらに縮小している | 同じ端末でプレビューと会場画面の直接表示を比較。ブラウザズーム100%、同じ表示領域で親要素の倍率を記録 |
| 古いタブ、キャッシュ、Service Worker（使用時）により別ビルドが動く | 会場とプレビューで配信JS・CSSの識別子、変更した箇所の実効スタイルを確認。新しいブラウザプロファイルでも比較 |
| OSの拡大率、外部画面の非ネイティブ解像度、複製表示、テレビのオーバースキャン | PC側の同じPNGを内蔵画面と会場画面に等倍表示。出力解像度とパネル解像度、テレビ側の画面サイズ設定を確認 |
| テレビの動き補間、ノイズ低減、過度な輪郭強調、液晶の残像 | ファイル自体は鮮明で会場画面の動きだけ不自然なら、同じ録画をPCとテレビで再生。テレビのPC／ゲームモード、各映像処理を個別に比較 |
| 無線投影、リモートデスクトップ、配信・録画の圧縮が動きの多い場面で画質を落とす | 利用している場合は元PCで直接見た画面と受信側を比較。有線直結やローカル再生で消えるか確認 |
| 出力のリフレッシュレートや変換器・分配器、色信号の間引き | PC側が正常な場合、機器を介さず同じモニターに直結して比較。静止中も色付き細文字だけにじむか、動くときだけ違うかを記録 |
| スマホで撮った映像だけがぼける | PCで保存した画面と肉眼での表示を照合。撮影でのみ再現するならカメラの自動焦点・手ぶれ・シャッターと表示周期を確認 |

## 4．最短で原因を絞る試験順

| 順番 | 変更するもの | 結果から決める次の手 |
| --- | --- | --- |
| 1 | 変更なし。固定目印と演出時刻を記録 | 最初に異常が出るコマ、影響範囲、終了後に戻るかを確定 |
| 2 | 寄った表／全体表を片方ずつ不可視にする。配置・タイマーは維持 | 両方単独で鮮明なら、重ねる対象と座標が修正対象。片方だけでもぶれればその表を追う |
| 3 | 表を1枚にした状態で着地前後の座標と寸法を比較 | 数値が飛ぶならカメラ・サイズ計測・スクロールへ。数値が不変なら上位レイヤー・合成へ |
| 4 | 同じ演出で後続の状態反映だけ一時保留 | 現象が消えれば再取得・再マウント・旧タイマーを個別に再現 |
| 5 | 固定文字まで変わるなら全面レイヤーを個別に停止。コマが飛ぶなら描画時間を計測 | 最初に改善した要素を元へ戻し、同じ条件で再発するかを確認 |
| 6 | PC側の記録では再現しない場合は会場への出力経路を比較 | 同じ記録を使い、どの画面・どの接続から差が出るかを特定 |

## 5．原因が分かった後の修正方針

- **表の二重像なら**、進出時には表を1枚表示し、その上で写真と接続線を動かす。全体表示への移行が必要なら、同じ文字が違う位置で同時に読める時間をなくす。開幕ツアーの寄りは独立して維持できる。
- **座標の往復なら**、書き換えている処理を特定し、演出中のカメラ位置を決める箇所を一つにする。写真読み込みで親サイズが変わる場合は枠の寸法を先に確保する。
- **状態の再適用なら**、同じ進出イベントは一度だけ開始し、画面を離れた演出のタイマーを破棄する。本当に次の試合へ進んだ場合は新しいイベントとして扱う。
- **描画負荷または表示経路なら**、計測で差が出た画像処理・演出・機材設定だけを変更する。

**完了条件**は、同一の登録写真で「表示を確認する」と会場表示の双方を再生し、2回戦→3回戦の着地・全体表示への切替・演出終了後に、離れたチーム名が二重に映らず、固定文字が揺れないこと。さらに、写真が正しい枠へ1回だけ入り、中央の線、枠の点灯、開幕の寄りが意図どおり残ることを確認する。
