# ダーツトーナメント演出システム 要件定義書

- 版数: v2.0（再設計版）
- 作成日: 2026-07-31
- 対象: React + GSAP + Supabase / Vercel デプロイ済み環境の改修

---

## 0. この版の位置づけ

v1 は「進行が動くこと」を目的に構築され、デプロイまで完了している。
v2 は以下の 3 点を目的とした再設計である。

1. **演出の質を上げる**（対戦カード・勝敗演出・オープニング・抽選演出）
2. **大会ごとの差し替えを、コードを触らずに完結させる**（大会名・広告・注意事項）
3. **当日のトラブルに耐える**（復帰・戻し・軽量化・プリロード）

### スコープ外（明示的にやらないこと）

- マルチテナント化、他店舗への販売・貸し出し
- 組織単位の権限管理、課金
- ネイティブアプリ化

単一 Supabase プロジェクト・単一運営主体を前提とし、その代わりに
**「後から機能を足せる余白」をスキーマ側に持たせる**方針とする（3.6 参照）。

---

## 1. 用語定義

| 用語 | 意味 |
|---|---|
| Admin | 運営が操作する画面。スマホ / PC 両対応。唯一の状態変更元 |
| Display | 会場モニターに投影する画面。状態を購読して描画するだけ。操作機能を持たない |
| シーン | Display が今何を映しているかを表す状態。`event_state.scene` が唯一の真実 |
| 演出モード | `full`（メイン版）/ `short`（短縮版）/ `lite`（軽量版）の 3 段階 |
| ブラケット | `winners` / `losers` / `grand_final` の 3 系統 |
| プレイリスト | オープニング・試合間などで流す動画/画像の並び。差し替え可能なデータ |
| 抽選セッション | 組み合わせを確定させた 1 回分の記録。演出はこれを再生するだけ |

---

## 2. 設計原則（すべての実装判断の上位ルール）

### 原則 1: 抽選結果と演出を完全に分離する

組み合わせは**演出の開始前に確定し、DB に保存する**。演出は確定済みデータの再生に過ぎない。

- 演出中に Display がリロード・切断しても結果が変わらない
- `full` / `short` が「同じデータの再生モード違い」で済む
- フルランダムとレーティングバランスの分岐が演出コードに漏れない
- 「演出中の操作で結果が変わった」という疑念が構造的に発生しない

**禁止事項:** 演出コンポーネントの中で乱数を引いてはならない。

### 原則 2: 画面はシーン状態機械で駆動する

Admin は `event_state` の 1 行を書き換えるだけ。Display はそれを購読して描画するだけ。

手動クローズ・演出スキップ・1 手戻す・再接続時の復帰が、すべて
「状態を書き換える／読み直す」という同一の仕組みに乗る。

**禁止事項:** Admin から Display へ「演出を再生せよ」という一過性の命令を送ってはならない。
命令は取りこぼされるが、状態は取りこぼされない。

### 原則 3: テンプレ固定 + 実行時差し込み

演出テンプレートは 1 本。大会ごとに変わるもの（大会名・広告・注意事項・配色）は
すべて DB のデータとして差し込む。

**判定基準:** 「次の大会でこの値は変わるか？」が Yes なら、それはコードではなくデータである。

### 原則 4: 表示は常に計算可能なデータから導く

レグ得失点は使わない運用でも、常に格納可能な構造にしておき、
表示は `events.show_scores` で切り替える（v1 からの継承方針）。

## 3. 機能要件

### 3.1 シーン状態機械

Display が取りうるシーンは以下の 10 種。

| scene | 内容 | 次への遷移契機 |
|---|---|---|
| `idle` | 待機（黒画面 + 接続状態） | Admin 操作 |
| `opening` | 大会タイトル → プレイリストをループ再生 | Admin 操作 |
| `draw` | 抽選・チーム編成演出 | 演出完了で自動 or Admin 操作 |
| `bracket` | トーナメント表の全体表示（既定の待機画面） | Admin 操作 |
| `vs_card` | 次の対戦カード（VS 演出） | **Admin が手動で閉じる** |
| `match_live` | 試合中。ブラケット + 現在試合をハイライト | Admin が勝敗を確定 |
| `result` | 勝敗演出（拡大・暗転・花びら） | 演出完了で自動 → `bracket` |
| `interval` | 試合間。広告プレイリストをループ | Admin 操作 |
| `award` | 表彰・最終結果 | Admin 操作 |
| `finished` | 終了 | — |

#### 状態遷移の実装ルール

- `event_state.scene_seq` は遷移のたびに単調増加させる。
  Display は自分が保持する seq より小さい更新を無視する（順序逆転・重複配信への耐性）。
- `awaiting_operator = true` の間、Display は演出を保持し、
  画面隅に小さく「操作待ち」インジケーターを表示する。
  これが無いと、止まっているのか壊れているのか観客にも運営にも判別できない。
- Display は起動時・再接続時に `event_state` を読み直し、
  現在のシーンを**先頭からではなく完了状態で**復元する（演出の再生をやり直さない）。

### 3.2 対戦カード（VS）演出 — 更新.md 項目 1・2

**タイミング:** 直前の試合の勝敗演出が終わった後、**これから行う対戦**に対して表示する。

**クローズ:** 自動で閉じない。Admin の「対戦カードを閉じる」操作で `match_live` へ遷移する。

**演出シーケンス（result 側）:**

| 時刻 | 動き |
|---|---|
| 0.0s | 両チームを同サイズで並べて表示（`match_live` からの継続） |
| 0.0–0.2s | 全体を軽く暗転 |
| 0.2–0.9s | 勝者を 150% へ拡大しながら輝度を上げる |
| 0.5–1.2s | 敗者を 75% へ縮小し、周囲を暗転させて沈める（勝者より遅らせる） |
| 1.0s– | 花びら演出をオーバーレイ |
| 3.5s | 完了。`bracket` へ自動遷移 |

**実装上の注意:**

- 拡大と縮小を**同時に開始しない**。勝者を先行させることで「勝った」感が出る。
- 花びらは常時パーティクル生成ではなく、**透過 WebM を 1 本重ねる**。
  既存の透過 WebM 生成資産を流用する。パーティクルは非力な会場 PC で破綻する。
- `lite` モードでは花びら WebM を静止画に、拡大縮小を CSS transition に落とす。

### 3.3 Winners / Losers の識別 — 更新.md 項目 3

**方針: ページを分けない。同一画面のテーマを丸ごと切り替える。**

ページ遷移を増やすと、リロード時の復帰と 1 手戻す操作が指数的に複雑化する。

`matches.bracket` の値をテーマキーとして、以下を一括で切り替える。

| 対象 | winners | losers | grand_final |
|---|---|---|---|
| アクセントカラー | シアン系 | ピンク／マゼンタ系 | ゴールド系 |
| フレーム装飾 | 実線 | 破線／欠けたライン | 二重線 |
| 効果音セット | 通常 | 低音寄り | ファンファーレ |
| 帯表示 | `WINNERS ROUND n` | `LOSERS ROUND n` | `GRAND FINAL` |

帯は VS 画面・試合中画面の両方に常時表示する。初見の観客が 1 秒で判別できることを条件とする。
配色の既定値はコード側の定数、上書きは `events.theme` で行う。

### 3.4 オープニングと広告 — 更新.md 項目 4・6

**プレイリストとして設計する。** シーン専用の実装にはしない。

`{ 種別, メディア, 表示秒数, 並び順 }` の配列を回す汎用プレーヤーを 1 つ作り、
`opening` / `interval` / `standby` / `award` のすべてで使い回す。

**構成:**

1. 大会タイトル表示（`events.title` / `subtitle` を差し込み。演出は統一）
2. 続けて注意事項スライド・動画 → 広告 → ループ
3. 試合開始まで回り続ける

**ロック機構:**

- 注意事項の項目は `playlist_items.is_locked = true` とし、UI から削除・無効化できない。
- 広告項目は大会ごとに自由に追加・削除・並べ替えできる。

**メディアの置き場所（Storage / 外部 URL 両対応）:**

| 用途 | 推奨 | 理由 |
|---|---|---|
| 注意事項動画・スライド | **Supabase Storage**（MP4 / 画像） | 確実に流す必要がある。外部埋め込みは自動再生・ループ制御が提供側の仕様に依存する |
| 花びら等の演出素材 | **Supabase Storage**（透過 WebM） | プリロード対象 |
| 広告 | **外部 URL 可**（YouTube 等） | スポンサー側が差し替える運用に強い |

`media_assets.source` で両者を吸収する。外部 URL の項目には
「自動再生が失敗する可能性がある」旨を Admin 画面に注意表示する。

**広告表示ログ:** 表示のたびに `ad_impressions` へ記録する。
スポンサー店舗へ「今回◯回表示しました」と報告でき、後付けが困難なため初期実装に含める。

### 3.5 チーム編成と抽選演出 — 更新.md 項目 5・7

#### 抽選モード

| モード | 挙動 |
|---|---|
| `full_random` | 完全ランダムでペアを組む |
| `rating_balanced` | レーティング差が均等になるようペアを事前決定する |
| `manual` | 運営が手動で組む |

**いずれのモードでも、`draw_sessions` に確定結果と `reveal_order` を保存してから演出を開始する。**

`reveal_order` は参加者 ID の配列で、
**「先頭から順に表示し、奇数番と偶数番を組にすると、確定済みチームが再現される」**
という不変条件を満たすように構成する。

- `full_random`: シャッフル結果をそのまま `reveal_order` にする
- `rating_balanced`: 確定ペアを崩さないよう、ペアが隣り合う順に並べる
- チーム人数が 3 以上（トリオス）の場合は「n 人ごとに 1 チーム」に一般化する

これにより、演出コードは抽選モードを一切知らずに済む。

#### 演出（short 版）

1. 参加者カードが一斉にずらりと並ぶ
2. ペアになる者同士がレーザービームで結線される
3. 1 チームずつ紹介
4. 組み上がったチームがトーナメント表の位置へ配置される

#### 演出（full 版）

1. 参加者を 1 人ずつ表示
2. 全員のカードがカルーセルで流れる
3. 全カードが中心の光に吸い込まれる
4. 裏返しのトランプが大きく表示される
5. ダーツが飛んできて刺さる
6. トランプが反転し、参加者が現れる（4–6 を人数分繰り返す）
7. 奇数番・偶数番でチーム化され、トーナメント表へ配置される

**リスクと対策:** full 版は所要時間が参加者数に対して線形に伸びる。
16 人 × 1 人 8 秒で 2 分を超える。

- 1 人あたりの尺を Admin から事前に設定可能にする（既定 6 秒 / 範囲 3–12 秒）
- 演出中いつでも `short` へ落とせる緊急スキップボタンを Admin に常設する
- Admin に「この設定での想定所要時間: 約 n 分 n 秒」を事前表示する

#### レーティングの後編集とロック

大会の進行状況によって編集可能範囲を制限する。無制限に編集できると当日の混乱時に復旧不能になる。

| `events.status` | 参加者の追加削除 | レーティング・表示名・写真 | 組み合わせ | 試合結果 |
|---|---|---|---|---|
| `draft` / `entry` | 可 | 可 | — | — |
| `drawn` | 不可 | 可 | 可（再抽選） | — |
| `running` | 不可 | 可 | **不可** | 可（1 手戻す） |
| `finished` | 不可 | 不可 | 不可 | 不可 |

例外的な差し替え（欠員対応など）は専用の「修正モード」に隔離し、
必ず `operation_log` に記録を残す。

### 3.6 拡張の余地（後から足せるようにしておく箇所）

単一プロダクトであってもここだけは緩く作る。

- `events.settings` (jsonb): 演出の尺、有効/無効フラグなど。新項目の追加にマイグレーション不要
- `events.theme` (jsonb): 配色の上書き
- `matches.layout` (jsonb): 座標駆動レイアウトの座標値
- `media_assets.source`: 保管先の追加（将来 CDN を足す等）に列追加で対応可
- ステータス系の列は **enum 型ではなく text + CHECK 制約**とする。
  値の追加が `ALTER TABLE ... DROP CONSTRAINT / ADD CONSTRAINT` で済み、`ALTER TYPE` の制約を受けない

## 4. 非機能要件

### 4.1 当日のトラブル耐性（最優先）

| 要件 | 実装 |
|---|---|
| Display の再起動から 5 秒以内に現在シーンへ復帰する | `event_state` の読み直しによる状態復元 |
| 会場 PC が非力でも破綻しない | `presentation_mode = 'lite'` で CSS トランジションのみに落とす |
| 音声が鳴らない事故を防ぐ | Display 起動時に「開始」クリックを 1 回挟み、AudioContext を解放する |
| 素材未取得のまま本番が始まらない | `media_assets.preload = true` の資産のプリロード完了率を Admin に表示 |
| 解像度差を吸収する | 1920×1080 基準で描画し、`transform: scale()` で実解像度に合わせる |
| 誤操作からの復旧 | `operation_log` による 1 手戻す（before / after のスナップショット方式） |

### 4.2 パフォーマンス

- Display の描画は 30fps を下回らないこと（`lite` モードは 60fps 相当）
- Realtime の反映遅延は 1 秒以内を目標
- 参加者 32 名までを性能設計の上限とする

### 4.3 セキュリティ

Admin のアクセス制御は現状どおり「URL + イベント ID 共有」方式を維持する。

**明示的に受け入れるリスク:** URL を知る者は誰でも進行を操作できる。
仲間内利用が前提のため許容するが、以下の軽減策は実装する。

- `events.admin_token` を持ち、Admin 画面はトークン付き URL でのみ開く（アプリ層での検証）
- `events.status = 'finished'` のイベントは RLS レベルで更新を拒否する
- Display 用 URL には Admin 機能を一切含めない

## 6. 実装フェーズ

演出を足す前に、進行の骨格を作り直す。順序を入れ替えないこと。

| フェーズ | 内容 | 完了条件 |
|---|---|---|
| **P0** | スキーマ再設計・移行 | 新スキーマで既存の進行が動く |
| **P1** | シーン状態機械への置き換え + W/L テーマ切替 | Display リロードで現在シーンへ復帰できる |
| **P2** | VS 演出・勝敗演出の刷新 | 更新.md 項目 1・2 を満たす |
| **P3** | プレイリスト（オープニング・広告・注意事項） | ここで一度実運用に投入する |
| **P4** | 抽選演出 short 版 + ロック機構 | 更新.md 項目 5・7（短縮）を満たす |
| **P5** | 抽選演出 full 版 | 更新.md 項目 7（メイン）を満たす |
| **P6** | 表彰演出・結果画像の自動生成・QR エントリー | — |

P3 完了時点で実運用に投入し、実際の大会でのフィードバックを P4 以降に反映する。
