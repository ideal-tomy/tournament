# 演出の滑らかさ・映像不具合の修正案

調査日：2026-11-20  
対象：会場 Display の開幕、ペア発表、ブラケット、試合結果、待機・表彰演出  
状態：コードと素材の静的調査に基づく提案。実機・デプロイ先の再現、性能計測、修正は未実施。

## 方針

- 現在の構図、順序、色、音、各シーンの所要時間を原則維持する。演出自体を削る前に、つなぎ方と処理を改善する。
- ブラケットのぼやけ、カメラの速度変化、ループの継ぎ目を優先して実画面で特定する。見た目が似た現象でも原因を決めつけない。
- 動画や音声の置き換え、画質・解像度の変更、タイミングの大幅変更は、効果と見た目を比較してから判断する。
- 大会の進行状態、複数端末間の同期、操作可能になる時刻は維持する。演出開始時刻の変更は、それらへの影響を確認してから行う。

## 修正候補

### 1. ブラケットのカメラの速度をつなぐ【優先度：高】

**現状・根拠**：開幕ツアーは全体表示から初戦へ寄り、横移動し、全体に戻る。寄りは終点に向かって加速する一方、横移動は停止状態から始まる。横移動から戻る境界も速度が一致せず、位置は連続していても動きが急に変わる。`src/features/presentation/openingTourTiming.ts` の `openingTourViewAt`。

**案**：現在の始点・終点、表示範囲、各区間の秒数を維持し、各区間の境界で速度が滑らかにつながる補間にする。まずは境界で自然に減速・再加速する案を比較し、必要なら移動方向と速度を連続させる経路を検討する。

**演出への影響**：寄り終わりの加速感や、横移動の始まり・終わりのテンポは少し変わる。構図と全体の長さは維持可能。動きを止めるか流し続けるかで印象が違うため、録画を並べて確認する。

**確認**：8・16・32チーム相当で各境界を動画確認し、始点・終点・秒数と全チームの表示を既存テストでも確認する。

### 2. 勝ち上がり時の二重表示・ぼやけを調べて改善【優先度：高】

**現状・根拠**：`src/checkin/AnimatedBracketAdvance.tsx` は寄り画面と全体画面を別々に描画し、3〜6秒付近で透明度を交差させる。両画面の縮尺・位置が違う間は、同じ文字や線が重なって二重・ぼやけに見える可能性がある。ウィナーズ側の寄り画面には CSS 拡大も使う。これは開幕ツアーとは別の演出であり、実際に指摘された場面かは未確認。

**案**：まず時間を固定した連続画像と実機動画で二重表示と拡大時の画質を確認する。原因が重なりなら、切り替え時の重複を抑えるフェード、または同じ表を一つのカメラで引く方式を試作する。線の描画、勝者の出現、点滅、6秒の進行を保持する。CSS 拡大の画質が原因なら SVG の表示範囲を使う方式も比較するが、描画負荷が増える可能性を計測する。

**演出への影響**：現状のふわっと溶け合う表現が短くなる、またはカメラが引く表現に変わる可能性がある。構図と勝ち上がりの順序は維持する。

**確認**：ウィナーズ・ルーザーズ・決勝、不戦勝や進出先がない場合を含め、線の接続位置、顔・文字、ちらつき、切り替え時の重なりを確認する。

### 3. ループの継ぎ目をなくす【優先度：高】

**現状・根拠**：背景の紙吹雪は位置を一定距離移動した後、開始位置に戻して繰り返す（`src/features/presentation/backdrop/appendPresentationBackdrop.ts`）。素材の端が一致しなければ戻る瞬間に飛ぶ。チーム一覧は同じページ群を２組並べて１組分移動しており、継ぎ目を隠す構造になっている（`src/features/presentation/scenes/DrawStage.tsx`）。実際の継ぎ目が滑らかか、どのループが指摘対象かは未確認。

**案**：対象を録画で特定する。紙吹雪なら同じ素材を複数枚連結して端が画面内に現れないようにする、または透明度を重ねて戻りを隠す。チーム一覧なら実際のページ幅と移動距離、拡大率変更時の再計算、１ページ・端数ページを検証し、ずれがある場合のみ補正する。待機動画の場合は動画の先頭・末尾を確認し、映像自体の継ぎ目なら素材側の処理も別途比較する。

**演出への影響**：速度や方向は原則維持。重ねる方式では紙吹雪の密度や明るさが一時的に変わる可能性がある。チーム一覧の表示順は変えない。

**確認**：開始直後と少なくとも２周分を、１・複数ページ、端数あり、画面サイズ変更後で確認する。

### 4. 初回の画面切り替えと写真準備を安定させる【優先度：高】

**現状・根拠**：`src/checkin/useTournamentState.ts` は原則１秒ごとに状態を取得し、`preparePortraits` の取得・デコードを待ってから反映する。演出はサーバーの経過時間から開始・再開するため、遅れて表示された場合に途中から始まる可能性がある。写真はページ内メモリで再利用される。実際の遅延や D1 の処理時間は未計測。

**案**：状態取得、写真取得・デコード、画面反映の時間を個別に計測する。次のシーンで必要な写真を可能な範囲で先読みし、重複取得を避け、準備完了後は即座に描画できるようにする。１枚の失敗が全体に与える影響や再試行も確認する。演出を端末ごとに最初から再生する変更は、他端末と進行時刻のずれを生むため採用前に別途設計する。

**演出への影響**：正常時の内容・秒数は維持する。写真が遅い場合の表示開始や代替表示は改善案によって変わり得るため、同期と併せて比較する。

**確認**：初回／キャッシュ済み、低速通信、写真取得失敗、再接続、タブ復帰、複数 Display で進行と操作可能時刻を確認する。API 応答時間だけで DB が原因と判断しない。

### 5. 描画負荷の高い場面を限定して軽くする【優先度：中】

**現状・根拠**：大きな背景の拡大・回転、複数レイヤーの合成、SVG フィルター、ぼかしや発光がある。`presentationBackdrop.css`、`ceremony/ceremony.css`、`vsBoard/vsBoard.css` など。実際のボトルネックは端末・ブラウザー次第で未計測。

**案**：本番相当の解像度・チーム数でフレーム時間、長い処理、画像デコードを計測し、重いシーンだけを対象にする。見えないレイヤーのアニメーション停止、同一レイアウト計算の再利用、フィルター領域の縮小などを比較する。`viewBox` 更新を CSS transform に置き換える場合は、拡大時の文字・画像の鮮明さと GPU メモリを含めて比較し、一律には置き換えない。

**演出への影響**：見えない処理の停止は原則なし。フィルター領域や描画方式の変更は光の広がりや文字の鮮明さに差が出る可能性がある。全体の動きやエフェクトを一律に削らない。

**確認**：開幕、ペア発表、勝ち上がり、VS、優勝を実際の会場端末で比較し、重い箇所のフレーム時間と見た目を記録する。

### 6. 素材の読み込みを分散・最適化する【優先度：中】

**現状・根拠**：公開素材には約10.5 MBの `vs-idle.mp4`、約6.9 MBのペア音声、約5.1 MBのオープニング音声、2 MB前後の画像がある。ファイルの存在だけでは、各シーンで実際に読み込まれるか、再生中のコマ落ちに影響するかは分からない。

**案**：ネットワーク記録で実際に使用する素材と取得時刻を特定し、必要な次シーンを余裕を持って先読みする。使用していない素材は配信経路を確認してから整理する。画像・動画・音声の再圧縮は画質・音質・ループ点を比較した別案とし、通信とデコード双方を計測する。

**演出への影響**：先読みの調整は原則なし。再圧縮や解像度変更は画質・音質やループ境界が変わり得るため、現行素材と比較する。

**確認**：初回と再訪問、通信制限時の読み込み時間、再生開始、音ずれ、動画の継ぎ目を確認する。

### 7. シーンの再生成・復帰時の飛びを確認する【優先度：中】

**現状・根拠**：`DrawControl.tsx` はシーン識別子をキーに演出を生成し、経過時間を初期再生位置に渡す。フォーカス・オンライン復帰時にも状態を再取得する。再生成や復帰の瞬間に演出が飛ぶ可能性はあるが、通常再生で頻発するかは未確認。

**案**：シーンの生成・破棄、状態更新、経過時間を記録し、不要な再生成がある場合だけ抑える。復帰時は正しい現在状態への追従を維持しつつ、読み込みと表示の境界を安定させる。

**演出への影響**：通常再生は維持。復帰時の追いつき方は、同期を保つため途中からの再開が残る場合がある。

**確認**：表示中の画面切替、スリープ復帰、通信断・再接続、進行中の運営操作を複数端末で確認する。

## 実施順と判定

1. 実際に問題が見えるシーンを特定し、現行動画・画面サイズ・チーム数・端末・通信条件を記録する。デプロイ先の調査は既存データを変更しない範囲で行う。
2. ブラケットの速度境界、勝ち上がりの重なり、対象ループを小さく修正し、同条件で前後を比較する。
3. API・写真・描画の時間を測り、原因に応じて先読みや描画負荷を改善する。容量削減は効果が確認できた素材から検討する。
4. 既存のテストとビルドに加え、各演出の開始・終了・進行、複数端末同期、画像・音声、再接続を確認する。

**完了の目安**：指摘された場面で急な速度変化・意図しない二重表示・ループの飛びが確認条件下で解消し、演出時間と大会進行が維持されること。性能改善は対象端末で前後の計測値を示す。未再現の現象は未解決として残す。

## 追加調査：ルーザーズ表の寄り・引きと枠の発光

### 観察対象と現状

ご指摘の「数秒おきに微妙に寄ったり離れたりする」「枠が光るとぼやける」現象について、`src/features/bracket/LosersColumnBoard.tsx`、`src/checkin/draw.css`、`src/checkin/FlowPresentation.tsx`、`src/checkin/AnimatedBracketAdvance.tsx` を追加で確認した。以下はコード上の根拠であり、実画面で周期や原因を確定したものではない。

**カメラの再計算**：ルーザーズ表は、対象の回戦または試合の位置を計測し、表全体に `translate` と `scale` を設定して画面に収める。通常表示ではその transform に 0.8 秒の transition が設定されている。表のデータから作る `columns` は描画のたびに生成され、カメラの位置を決める effect の依存値に入っている。そのため、親からの再描画で表示対象が同じでも effect が再実行され得る。計測処理は一度 transform を `none` にしてから配置し直すため、この操作と transition が組み合わさると不意の移動・拡縮や計測値の揺れが起きる可能性がある。再描画が何秒おきに起きるかは状態の変化次第であり、コードだけでは実際の周期は断定できない。なお試合に寄る `is-framed` 表示では transition は無効になっている。

**枠の発光**：対象の枠には１秒周期で枠色、6px の広がり、および最大 22px のぼかしを含む `box-shadow` が繰り返し適用される。これは光がぼんやり広がる意図的な表現だが、拡大された表ではぼかしも目立ち、画面全体がぼやけたように感じる可能性がある。発光は枠に対する処理で、文字そのものに blur を指定しているわけではない。発光の描画負荷がカクつきに結びつくかも未計測。

**勝ち上がり時の重なり**：勝ち上がり演出では、寄りのルーザーズ表と回戦全体の表を別々に表示し、3〜6秒にかけて透明度を交差させる。両方で進出先の枠が発光し得るため、異なる位置・倍率の枠や文字が重なってぼやける可能性もある。通常の表表示と勝ち上がり演出は分けて確認する。

### 追加の修正案【優先度：高】

1. **同じ内容でカメラを再配置しない**：列データの参照を安定させる、または effect の依存値を表示位置に必要な安定した情報に絞り、対象回戦・試合・実際の画面サイズが変わらない限り再配置を発生させない。実際に対象が変わったときの 0.8 秒の移動は原則残す。
2. **計測中の変形を画面に出さない**：現在の transform の解除と再設定による影響を、transition を一時的に抑える方法や、表示中の要素を変形解除せずに元の座標を計測する方法で比較する。計測に伴うレイアウト負荷も確認する。画面サイズ変更時も正しく収める。
3. **光る枠と中身を分離する**：枠の強調と１秒周期は残し、光だけを枠専用の別レイヤーに置いて、ぼかしの広がり・明るさを必要最小限に調整する案を比較する。文字・写真は鮮明なままにし、枠の位置や大きさを変えない。負荷についても変更前後で計測する。
4. **勝ち上がり時の二重表示を抑える**：該当する場合、寄りと全体の切り替え中に重複する文字・枠・発光を抑える方式を比較する。勝ち上がり線、進出先の強調、全体６秒の長さを維持する。

### 演出への影響と確認

不要な再配置を止めれば、同じ回戦を表示している間の微妙な寄り引きはなくなる見込み。実際の回戦切り替え時の移動は残す。発光の修正では光のにじみや明るさが少し変わり得るため、現行の「光っている」印象を残した複数案を比較する。勝ち上がりの重なりを減らす場合、表が溶け合う印象は変わる可能性がある。

同じ回戦を少なくとも数十秒表示し、１秒の発光周期と、再描画・カメラ transform・対象回戦の変化を記録する。通常表示と勝ち上がりを分け、複数試合の同時進行、回戦変更、画面サイズ変更、復帰時も確認する。枠・文字・顔の鮮明さと移動の前後動画、フレーム時間を比較し、対象が変わった場合だけカメラが動くことを確認する。
