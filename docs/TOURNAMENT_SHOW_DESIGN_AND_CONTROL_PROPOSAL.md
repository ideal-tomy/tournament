# トーナメント演出・進行制御 改善提案書

**対象リポジトリ:** [ideal-tomy/tournament](https://github.com/ideal-tomy/tournament)  
**作成日:** 2026-10-12  
**位置づけ:** 今後の企画・UX設計・実装方針を定める正本。各Phaseの着手は本書に沿って個別に行う。  
**対象:** 会場Display、運営Admin、抽選、試合進行、対戦カード、勝敗発表、優勝・表彰、演出素材、リハーサル。

---

## 1. 目的と到達点

目指すのは「アニメーション付き大会管理画面」ではなく、**大会進行そのものを一つのショーとして成立させるシステム**である。

テレビのスポーツ番組や完成度の高い対戦ゲームに近い体験を、ブラウザ上で実現する。ただし、豪華な演出が大会運営の確実性を損なってはならない。

### 実現したい体験

1. 観客は「今、何が決まり、次に何が起きるか」を説明なしに理解できる。
2. 抽選結果、対戦相手、勝者、勝ち上がり、優勝者が明確に伝わる。
3. 選手やチームの顔写真・名前が見せ場の主役となる。
4. 映像、動き、SE、BGM、静寂のタイミングが一体化している。
5. 同じ人物・チームの表示が突然消え、別の場所に再登場する違和感がない。
6. 司会者、拍手、会場の進行に合わせて運営者が止める・進める・省略する判断ができる。
7. 通信・素材・音声のトラブルでも大会の進行を止めない。
8. 大会の規模に応じて演出時間を変えられる。

**優先順位:** 正しい勝敗・対戦情報 ＞ 当日の運営安全性 ＞ 観客の理解しやすさ ＞ 映像・音の迫力。

## 2. 調査で確認できた現状と、提案を区別する

### 2.1 現行コード・調査報告から確認できたこと

| 項目 | 現状 |
|---|---|
| 基本構成 | React/Vite + Supabase。運営とDisplayの画面が分離されている。 |
| Displayの主系統 | `DrawScene` / `ResultScene` / `VsCardScene` / `BracketView`。 |
| 抽選 | カード、ダーツ、反転、参加者表示、ペア確定をGSAPで制御。`full / short / lite` がある。 |
| 抽選の保持時間 | `PAIR CONFIRMED` は7秒。32名・16チームのfull演出は計算上約5分24秒。 |
| 勝敗 | `ResultScene` の表示尺は5.8秒。勝者拡大、敗者縮小、花吹雪が中心。 |
| 次試合 | 勝者確定後、次試合があれば `vs_card` へ進む。最低5秒表示し、運営者が閉じて `match_live` へ進む。 |
| 最終試合 | `finished` 表示は現状 `FINISHED` 中心で、優勝者を主役にした専用演出が不足。 |
| 旧演出資産 | `EffectOrchestrator`、`PresentationStage`、`LineCollision`、`ExplosionVideo` などが残るが、現行Display主系統には統合されていない。 |
| 状態同期 | `scene` と `scene_seq` を使い、Supabase Realtime と1.5秒pollingで受信。 |
| 重要な不具合リスク | Displayから永続sceneを書き換えること、複数更新の非原子性、認証・認可、重いプリロード、E2E不足。 |

### 2.2 過去の設計検討から継承した、守りたい意図

過去の演出検討から、次の構想を本提案へ統合した。

- WIN → 勝者進出ライン → 対戦者が左右から接近 → **衝突と爆発は1回** → 同じ顔のままVS → 光とともにブラケットへ復帰。
- 黒一色への不自然な切り替えを避け、ブラケットと演出をつなぐ。
- 顔写真を消して再登場させない。
- 画面の因果関係（接近したから衝突、衝突したからVS）を観客に理解させる。
- 映像が空白になったり、爆発より後に接近したりする不具合を再発させない。

また、**WINNER → NEXT MATCH は自動、NEXT MATCH → 試合開始は必ず手動**という運営要件を継承する。

**本提案では、この2つを両立させる。** 過去資料の必要な意図は本書へ統合済みであり、本書と現行コードを今後の判断基準とする。

### 2.3 今回の新規提案（未実装）

- ショー全体の演出ルールとシーン別演出仕様。
- 「結果 → 勝ち上がり → 次試合」を連続映像として見せる共通ステージ。
- 専用Show Control（当日の演出操作画面）。
- 優勝・表彰に特化した `ChampionScene`。
- 演出プレビュー、時間位置指定、音声点検、素材ロード状況の見える化。
- Cloudflare移行時に利用する進行コマンドと複数Display同期の規則。

## 3. 全体の演出方針

### 3.1 迫力は「強弱」で作る

常時ネオン、爆発、点滅、揺れを入れない。**予兆 → 緊張 → 決定的瞬間 → 余韻 → 次の展開**を基本構造とする。

| 要素 | 使い方 | 避けること |
|---|---|---|
| 暗転 | 注目を集める、場面を切り替える | 理由のない真っ黒な時間 |
| 顔写真 | 選手・チームを中心に大きく扱う | 演出の途中で消えて何度も出現する |
| 動き | 勝ち上がり・衝突など「出来事」を表現 | 無意味な常時浮遊・揺れ |
| 光 | 勝敗、ペア決定、衝突、優勝の強調 | 毎回の画面全体フラッシュ |
| SE | ダーツ命中、カード反転、勝敗確定、VS衝突に同期 | 同一瞬間に音を重ねすぎる |
| BGM | 抽選、試合直前、優勝などの感情を支える | 司会者や会場音を邪魔する |
| 静寂 | 決定的瞬間の直前に短く使う | 素材待ちや通信待ちによる無音・停止 |
| テキスト | 勝者、チーム名、対戦、ラウンドを明快に表示 | 長文、細字、小さな装飾ラベルの乱用 |

### 3.2 ビジュアルの統一

- 画面は16:9の会場表示を第一基準にする。1920×1080を基準とし、1280×720、1366×768、4Kも検証。
- 深い黒・ネイビーを共通背景とし、アクセントは用途を絞る。青・シアンは通常の進行、金は勝者・優勝などの格上げに使う案。
- 既存の素材を先に棚卸しし、似た役割の画像・エフェクトを増やしすぎない。
- 大会タイトル・名前・写真・次試合の情報を優先し、不要な枠の重なりやデバッグ文字は除く。
- 観客向けDisplayには操作ボタン、`scene_seq`、event ID、接続技術情報を常時出さない。異常時のみ安全な案内を出す。

### 3.3 演出の共通文法

各シーンの見せ方を次の5段階で設計し、必要な段階だけ利用する。

```text
SETUP（状況提示）
  → ANTICIPATION（期待・緊張）
  → IMPACT（決定的瞬間）
  → REVEAL（結果を読ませる）
  → HOLD / HANDOFF（余韻・次へ受け渡し）
```

これらは**映像内の演出段階**であり、原則としてデータベースに1段階ずつ保存する`scene`ではない。

## 4. シーン別の演出提案

以下の秒数は**演出検証用の初期案**。正式仕様の固定値ではない。大会規模と会場でのリハーサル結果に基づき調整する。

### 4.1 OPENING：大会開始

**観客に伝えること:** いまから大会が始まる。

- 会場待機画面からタイトルをゆっくり登場させる。
- 音楽は小さく始めて印象的なタイミングでタイトルを確定。
- 大会名・開催情報を読める時間だけ保持する。
- オープニング用の動画がある場合は利用できるが、動画がない場合もタイトル演出だけで成立させる。
- 終了時は運営者が抽選など次のシーンへ明示的に進められる。

### 4.2 DRAW：チーム抽選・ペア決定

**観客に伝えること:** どの参加者が選ばれ、誰と誰が組むのか。

```text
カード裏面を見せる
  → ダーツが飛ぶ
  → 裏面に命中（SEと光）
  → ダーツ・穴・裏面の効果を除去
  → カード反転
  → 顔写真と名前を表示
  → 次のメンバーも同様
  → ペア確定：2人の顔と名前を同時に見せる
  → 次チームへ
  → 全組み合わせ／ブラケットへ
```

**守るべき既存条件**

- カード表面にダーツ穴を残さない。
- ペアが誰なのか視認できる保持時間を残す。現行fullの7秒は比較の基準として保存する。
- 抽選結果は先に確定し、Displayは結果を演出として再生するだけ。アニメーションで組み合わせを再抽選しない。
- `full / short / lite` を維持する。

**追加提案**

- 観客用の「現在何チーム目か」を控えめに表示。残り数が把握できる。
- 8名、16名、32名でテンポを変える。32名full（約5分24秒）は会場次第で長いため、人数別プリセットを用意。
- `short`でも「決定結果を見せる時間」を削りすぎない。
- 各チームの確定後、ステージを乱雑に全面リセットせず、次カードへ自然に移る。
- Adminに予想総尺と進行中のチーム数を表示する。

### 4.3 BRACKET：トーナメント全体像

**観客に伝えること:** 現在の大会状況と勝ち上がり。

- 顔写真中心のブラケット構成を生かし、必要な時だけ現在試合や勝者ラインを目立たせる。
- 確定済みと未確定の情報を混同しない。
- 動かすのは「変化が起きた経路」。全部の線を常時点滅させない。
- 勝者が進出する演出では、進出前・進出後の表示用スナップショットを明確に分ける。
- 重要な変化を確認できる短いホールドを設ける。

### 4.4 MATCH START / VS：対戦直前

**観客に伝えること:** 誰と誰がこれから戦うか。

```text
ブラケットから次の対戦2チームに注目
  → 2組を左右へ引き出す
  → 接近・衝突（必要な場面のみ）
  → 1回のインパクトSE・光
  → VSと顔写真・チーム名を明確に表示
  → NEXT MATCH / START待機
```

- 衝突は「接近の完了点」に同期させる。爆発を先に出さない。
- `VS`は衝突の余韻から現れるが、文字を読ませるために静止する時間を作る。
- 同じ選手の顔を再マウントして二重登場させない。
- 通常試合は軽め、準決勝・決勝は重厚、といった強弱を選択できる。
- **試合の実際の開始は運営者の手動操作。** `NEXT MATCH`画面の自動終了は禁止。

### 4.5 RESULT → BRACKET ADVANCE → NEXT MATCH：最優先で完成させる一連の見せ場

**観客に伝えること:** 誰が勝ち、その勝利によって大会がどう進み、次に誰と戦うか。

現在は `ResultScene` から `VsCardScene` へ切り替わる構造であり、過去に構想した連続演出のための接続が不足している。まずはこの区間を**一本の映像体験**として成立させる。

#### 推奨シーケンス（次試合がある場合）

| 順 | フェーズ | 見せる内容 | 時間の初期案 |
|---|---|---|---|
| 1 | WIN REVEAL | 勝者を明るく、敗者を控えめに。WIN表示 | 約0.7〜1.0秒で登場 |
| 2 | WIN HOLD | 勝者の顔・名前を確実に読ませる。周辺演出だけ動く | 約2.5〜3.5秒 |
| 3 | DISSOLVE | 勝者がブラケット内の元位置に対応する。背景の表が見え始める | 約0.5〜0.8秒 |
| 4 | ADVANCE | 勝者の進出ラインが出発点から進出先へ伸びる。先に到達済みにしない | 約1.2〜2.0秒 |
| 5 | OPPONENTS | 確定済みの次対戦者が左右から接近 | 約1.3〜2.5秒 |
| 6 | IMPACT | 中央で衝突。爆発・光・SEは原則1回 | 約0.4〜0.9秒 |
| 7 | VS REVEAL | 同じ人物のままVSと次試合情報へ移行 | 約0.5〜0.8秒 |
| 8 | NEXT MATCH HOLD | 顔・名前・ラウンド・対戦組み合わせを保持 | **運営者が試合開始するまで無期限** |

**重要:** これは各値を足して固定する自動再生時間ではない。実際には前後のフェーズを少し重ね、観客に不自然な空白や長すぎる待ちを感じさせない。

#### 必ず守る事項

- 勝者が出たからラインが伸びる、2組が接近したから衝突する、という視覚的な因果が成立する。
- ブラケットがすでに更新されていても、演出上の表示は**更新前→進出演出→更新後**を正しい順に見せる。
- 試合データの確定を「線が伸び終わるまで」遅延させない。確定処理と見せ方は分離する。
- 画像の読み込み待ちで顔のプレースホルダが突然切り替わる現象を抑える。
- 画面全体の黒フェード連発、同じ選手の複数回登場、爆発の多重再生を禁止。
- 次試合が成立していない、または次試合がない場合にはVSへ進めず、正しいブラケット／優勝へ分岐。
- 演出をスキップしても勝敗が取り消されたり、二重確定されたりしない。

### 4.6 CHAMPION：優勝発表（新設提案）

**観客に伝えること:** 大会の頂点に立った選手・チームは誰か。

```text
決勝結果が確定
  → FINAL WINNER（通常試合より長い余韻）
  → 一時的に光と音を絞る
  → 大会タイトルとCHAMPIONの予兆
  → 優勝チームの全メンバーが主役として登場
  → チーム名・選手名・トロフィー表現
  → 専用SE / BGM / 金色の演出
  → 写真撮影・拍手のための保持
  → 運営者が表彰へ進める
```

- `championTeamId`を実際の写真・名前表示に活用する。
- 優勝発表は**自動で消えない**。写真撮影や司会の進行に合わせ、Admin操作で次へ。
- 決勝後に誤って `NEXT MATCH` を表示しない。
- 素材がなくても大会名・優勝者名・基本背景で成立するフォールバックを持つ。
- 優勝演出は「大会終了処理」と分ける。**優勝した瞬間に顔写真を削除しない**。肖像データの削除は大会終了・運営確認後に別の安全な手順で行う。

### 4.7 INTERVAL / AWARD：休憩・表彰

- 休憩中は専用プレイリストや背景を表示し、試合用の過剰な動きを止める。
- 表彰は優勝発表と別の場面。運営が選手紹介や記念撮影を進められる。
- 動画が読み込めない場合はポスター画像・静的背景へ切り替える。
- 休憩から再開する操作、表彰から終了する操作を明確に分ける。

## 5. Show Control：運営者向け演出操作画面

既存の `/admin` は参加者登録・抽選・進行・メディア・シーン・終了・疎通などのタブが混在している。本番進行では、設定作業と「いま押すボタン」を分ける。

### 5.1 画面案

```text
┌────────────────────────────────────────────────────────────┐
│ SHOW CONTROL   大会名       LIVE / REHEARSAL   接続状態    │
├──────────────────────────────┬─────────────────────────────┤
│ 会場プレビュー               │ 進行情報                    │
│ 現在の映像（縮小表示）       │ 現在: RESULT / WIN HOLD    │
│                              │ 次: BRACKET → NEXT MATCH  │
│                              │ 対戦: TEAM A vs TEAM B    │
│                              │ Display: 2台 / 同期状態   │
├──────────────────────────────┴─────────────────────────────┤
│ [次へ進む] [一時停止] [再開] [演出スキップ] [安全表示へ] │
│ [音声チェック] [映像チェック] [進行履歴]                 │
└────────────────────────────────────────────────────────────┘
```

**「会場プレビュー」は同期された結果を見られることが重要。** 当初は実映像のライブミラーを必須にせず、同じscene/データで描画したプレビューと最新状態表示から始めてもよい。

### 5.2 操作の分類（誤操作防止）

| 操作 | 効果 | ルール |
|---|---|---|
| 次へ進む | 停止中の演出から次の演出／場面へ | 次の遷移先を必ず明示 |
| 一時停止 | 現在の演出タイムラインを停止 | DB上の勝敗・ブラケットは変更しない |
| 再開 | 同じ位置から演出を続ける | 重複SE、二重タイマーを発生させない |
| 演出スキップ | 演出を安全な最終表示へ移す | 勝敗結果や確定した対戦情報は変えない |
| START MATCH | NEXT MATCHから実際の試合中へ | **運営者が明示的に実行**、二重送信防止 |
| 勝敗確定 | 選んだ勝者を大会データへ確定 | チーム名と対象試合の確認、取り消し履歴 |
| 安全表示へ | 不具合時にブラケットまたは待機静止画へ | 進行データを巻き戻さない |
| 緊急停止 | 映像・音の激しい動きを止める | 直ちに静止・無音、必要に応じ安全画面 |
| 1手戻す | 大会進行データを修正 | **演出の巻き戻しとは別操作**。権限・確認・監査ログ必須 |

**大事な区別:** 「演出の前に戻る」「大会結果の確定を取り消す」「大会の全データを初期化する」は異なる操作。UIとAPIを混同しない。

### 5.3 本番画面と設定画面を分離

- **運営中の主画面:** 現在の試合、勝敗確定、NEXT MATCH手動開始、表示確認、スキップ、安全表示。
- **事前設定:** 参加者、抽選設定、演出プリセット、素材、BGM/SE、表示端末、表示確認。
- **管理者限定:** データ修正、戻す、イベント終了、肖像データ削除。
- **リハーサル:** 誤って本番データに書き込まない別イベント／環境として目立つように区別。

### 5.4 スマホ・タブレットでの運営

- 大きな操作ボタンと十分な間隔。
- 一画面に全設定を詰め込まず、「現在の進行」と「次の操作」を優先。
- 押下後は「送信中→確定→Display受信確認／再試行可能」を分けて表示。
- 重要な操作の誤タップ防止、二重タップ防止。
- 電波不良時に押せたように見えるだけのUIを禁止。

## 6. 演出システムの設計方針

### 6.1 大会データと表示演出を分ける

```text
[大会データの真実]
  試合・勝者・ブラケット・優勝者・履歴
             ↓ 確定された情報
[ショー進行の真実]
  scene / scene_seq / scene開始時刻 / 次へ進む条件
             ↓ 表示命令
[Display内の演出]
  GSAP Timeline / 画像 / 動画 / SE / BGM / ローカル進捗
```

- **大会データの確定**は信頼できるサーバー側のコマンドで行う。
- **表示sceneの変更**もAdminまたはサーバーが権威を持つ。Displayのアニメ完了をDB確定処理の主体にしない。
- **演出内部の0.2秒単位のフェーズ**はDisplay内のタイムラインで扱う。
- Displayは原則として受信、再生、再同期、完了通知（必要時のみ）に専念する。

### 6.2 シーン間の「同じ人物が連続して動く」設計

現行の`ResultScene`と`VsCardScene`を単にcrossfadeするだけでは、「顔が消えて再登場する」問題を完全には防げない。

**推奨:** 結果から次試合のVS確定表示までを、一時的に同じ表示ステージが管理できるようにする。

考えられる設計例：

- `PostMatchStage`（仮称）を追加し、WIN → ADVANCE → CLASH → VSを単一の演出舞台として制御する。
- サーバーの粗いsceneは現行の`result`/`vs_card`の互換性を慎重に検討する。必要なら、新しい論理sceneと旧シーンの対応表を設ける。
- ステージ内の顔・カードは位置、scale、opacityなどを変えて継続表示する。
- `NEXT MATCH`ホールド中は安定した最終フレームを維持し、START MATCHはサーバー側の許可コマンドでのみ実行する。

**いきなり既存scene名を変更しない。** まず最小の試作で、既存の勝敗確定・スキップ・再接続・手動開始と矛盾しない実装経路を確定する。

### 6.3 1つの演出に1つの時間管理

- GSAPの主タイムラインを時間の基準にする。
- Reactのmount/unmountや複数`setTimeout`で演出順序を決めない。
- 必要なDOMを先に用意し、参照がある状態でアニメーションを開始する。
- `seek`、`pause`、`resume`、`complete`、`kill/cleanup`を制御可能にする。
- scene変更／端末再接続／StrictMode等で、古い演出やSEを再生しない。

### 6.4 推奨する表示コマンド・状態（設計例）

```ts
// 実装仕様確定前のイメージ。現在のAPIには未実装。
type ShowCommand = {
  eventId: string;
  requestId: string;      // 冪等性
  expectedVersion: number;
  action:
    | 'CONFIRM_RESULT'
    | 'START_SCENE'
    | 'ADVANCE_SCENE'
    | 'PAUSE_SHOW'
    | 'RESUME_SHOW'
    | 'SKIP_PRESENTATION'
    | 'START_MATCH'
    | 'SHOW_SAFE_SCREEN';
  payload?: Record<string, unknown>;
};

type ShowState = {
  eventId: string;
  scene: string;
  sceneSeq: number;
  version: number;
  startedAt: string | null;

```

**注意:** これは設計例であり、現在の`Scene`型・`event_state`テーブルを直接書き換える指示ではない。pause/seekは会場全体で同期すべきか、プレビュー端末に限るかを実装前に決める。

### 6.5 Cloudflareへの移行と結びつける

先行の監査レポートを踏まえると、Cloudflare移行時は次の方向が合理的。

- Worker APIで認証・認可・進行コマンドを処理。
- D1で大会・シーン・操作ログの整合性を管理。
- R2で顔写真や演出関連メディアを管理。
- 大会eventごとのDurable Objectで進行コマンドの調停とDisplay配信。
- `requestId`、期待version、actorを扱い、二重クリックや複数Adminによる重複確定を防ぐ。
- **D1への保存成功後にのみ**確定sceneをDisplayへ通知する。

**同期の追加検討:** 複数Displayで同じ瞬間に衝突SEや画面を出したい場合、scene番号の配信だけでは不十分。開始予定時刻とタイムライン位置を共有し、時計のずれ・再接続・配信遅延を補正する。会場が1台のPCから映像分配する方式なら、より簡単な運用も選べる。

## 7. 音・素材・パフォーマンスの設計

### 7.1 音の優先順位

| 音種 | 役割 | 推奨動作 |
|---|---|---|
| BGM | 緊張感・世界観 | フェードイン／フェードアウト。場面ごとの音量プリセット |
| UI SE | カード移動、反転 | 小さく短く、連打時には抑制 |
| IMPACT SE | ダーツ命中、勝敗、衝突 | 映像の決定的な1フレームに同期 |
| CHAMPION | 最大の見せ場 | 専用の短い予兆、発表音、余韻を設計 |
| 無音 | 司会・会場の歓声、緊張 | 意図的な演出として使う |

- Display開始前に音声再生が許可されているか確認。
- 共有音声管理を使い、master volume・BGM・SEを調節可能にする。
- 音声がblocked/未ロードでも映像は続行し、運営に状態を通知。
- PC内蔵スピーカーだけでなく、会場設備で実際の音量・遅延を確認。

### 7.2 素材管理

- 既存の`tournament-effects`、`hit_explosion.webm`等を最初に台帳化。
- 各素材へ「使うscene」「目的」「代替」「ファイル容量」「ロード優先度」を付ける。
- 初回に全演出素材を一括必須ロードしない。**開始に必要なcritical**と次の場面に必要な**lazy**に分ける。
- WebP/AVIF/透過動画などを適材適所に用いる。容量だけでなく透過・色・再生互換も確認。
- 素材1つが読み込めなくても、画像の代替、CSS演出、静止画、無音で進行できる。
- プリロード進捗は擬似%ではなく実際の件数／容量／成功・失敗を表示。

### 7.3 派手な演出に対する安全設計

- `prefers-reduced-motion`へ対応し、視覚的な点滅や揺れを減らす。
- 高頻度の全画面フラッシュ、長時間の大きな画面揺れを避ける。
- 緊急停止・ライトな演出プリセットを用意。
- 4Kでの負荷を見越し、演出の種類と同時発火数を制限する。

## 8. 演出モードと尺の考え方

現在の`full / short / lite`は維持する。名称変更は必須ではない。以下は将来的な整理案。

| 用途 | モード案 | 目的 |
|---|---|---|
| 開会・決勝・表彰 | Cinematic | 静寂、SE、見せ場、ホールドを十分に取る |
| 一般の試合 | Standard | 必要な見せ場を保ち、長すぎない |
| 参加人数が多い抽選 | Compact | 結果の視認性を維持しながら進行を短縮 |
| 時間押し・低スペック・配慮 | Lite | 過度な動きや重い効果を省く |

**原則:** 大会の試合数が多いからといって、全試合で同じ長尺の衝突演出を繰り返さない。開会、準決勝、決勝、優勝で盛り上がりの階段を作る。

Adminでは演出開始前に推定尺を見せ、試合の途中でも安全に軽量モードへ変更できるようにする。ただし、再生途中のモード変更は「その場で途中の数値だけ置換」ではなく、明確な停止・次sceneから適用など、安全なルールを定める。

## 9. リハーサル・プレビュー環境

本番へ投入する前に、演出を短い単位で繰り返し確認できる環境を作る。

### 9.1 プレビューに必要な機能

1. シーン一覧から任意の演出を選択。
2. サンプルデータで表示（本番の勝敗や参加者を変更しない）。
3. 再生／停止／再開／スキップ。
4. タイムラインの任意位置へ移動して確認（**プレビューのみ**）。
5. 音あり／音なし、`full / short / lite`の切替。
6. 1920×1080を主基準とした画面確認。
7. 画像欠損、動画再生失敗、通信断、途中再接続の模擬試験。

**注意:** 映像編集ソフトのような大規模なタイムラインCMSは不要。まずはエンジニアが秒数と流れを確認できる最小限のプレビューで十分。

### 9.2 保存したい成果物

- 代表シーンごとのスクリーンショット。
- シーンごとの短い画面録画。
- 映像・音・操作のチェックリスト。
- 「理想」と「実際」の差分（問題発生時はスクリーンショットや動画の秒数で報告）。

**過去に起きた「1箇所直したら別の演出が壊れる」の再発防止が狙い。**

## 10. 実装前に決めること

1. **主系統:** `DrawScene`、`ResultScene`、`VsCardScene`を基準にし、旧`EffectOrchestrator`の必要な要素を移す。旧コードは動作確認後に削除する。無条件削除しない。
2. **最初の完成対象:** `RESULT → BRACKET ADVANCE → NEXT MATCH`。ここで映像と音の品質基準を作る。
3. **シーン境界:** 既存`result`/`vs_card`との互換を維持したまま、共有ステージをどう構築するかを比較する。
4. **会場構成:** 1出力分配なのか、複数独立Displayなのか。同期仕様の複雑さが変わる。
5. **運営操作の範囲:** 誰が勝敗確定、次試合開始、演出スキップ、データ修正を行えるか。
6. **演出開始ルール:** 自動開始／運営手動開始／司会待ちの境界を定義する。
7. **本番とリハーサル:** 参加者・写真・勝敗データの混線を防ぐ方法。
8. **素材の利用権限:** 顔写真と効果音／BGM／動画の扱いを確認する。

## 12. 受入基準（開発・検証で必ず使う）

### 演出品質

- [ ] 観客が勝者・次試合・優勝者を即座に認識できる。
- [ ] WINからNEXT MATCHまで、意味のない黒画面や未ロード空白がない。
- [ ] 勝者の進出ラインが、確定前に到達済みに見えない。
- [ ] 接近→衝突→爆発→VSの順序が毎回一致する。
- [ ] 衝突エフェクトと主SEが二重・三重に発生しない。
- [ ] 顔・名前が突然消えて再登場せず、同じ人物として連続して見える。
- [ ] NEXT MATCHは運営操作まで保持され、試合が自動開始しない。
- [ ] 決勝終了時には優勝者の顔・名前が主役として表示される。
- [ ] 優勝演出は写真撮影などが終わるまで保持可能。

### 進行制御

- [ ] 勝敗確定は複数タブ・二重タップでも一度だけ反映される。
- [ ] Displayは大会データ・永続sceneを勝手に確定しない。
- [ ] スキップ・一時停止が大会の勝敗を変えない。
- [ ] 途中リロードでも最新の確定状態へ安全に復帰できる。
- [ ] 二台以上のDisplayが同じscene/versionへ復帰する。
- [ ] 映像や音の欠損でも安全表示または静的画面で続行できる。
- [ ] 緊急停止と正常復帰の操作が明確。
- [ ] リハーサルが本番データに影響しない。

### テストと品質保証

- [ ] 既存のunit test・buildが成功。
- [ ] Playwright等で主要sceneのブラウザE2Eがある。
- [ ] 画面の重要フレームをスクリーンショットで比較できる。
- [ ] 本番端末・会場音響で動作確認済み。
- [ ] 認証・肖像データ・運営操作ログの本番要件を満たす。
